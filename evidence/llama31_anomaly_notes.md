# llama3.1:latest v20 sem_adv anomaly — findings

Source data: `AutoChipAdvFB/STITCHAdv/runs/resume_20260814_135236/v20/llama31_latest/{raw_adv,sem_adv}/`. Directive text was not persisted to disk by the runner (only `llm_response.txt` and `sim_log.txt` survive per iteration); it was reconstructed by re-running `run_verilator_lint` + `interpret_verilator` from `autochip_stitch_runner.py` against the exact saved `.v` file for each iteration, and cross-checked against the `interp_codes` recorded in each `metrics.json` — reconstruction matched the recorded codes on every one of the 44 iterations examined, so it can be trusted. Script: `phase2_reconstruct.py`; raw data: `phase2_reconstructed.json`.

## Important correction to the working hypothesis before the category breakdown

The brief for this investigation framed one candidate mechanism as "the model discards already-correct code in response to being told it's wrong." **That mechanism does not occur in any of the four modules.** Each condition (`baseline`/`raw_adv`/`sem_adv`) is a fully separate process invocation of `run_one_condition` starting from an empty message history — iteration 1 of `sem_adv` is an independent LLM sample from iteration 1 of `raw_adv`, generated from the identical system+spec prompt but at `temperature=0.1` with no fixed seed. There is no shared code lineage between a `raw_adv` pass and a `sem_adv` run — `sem_adv` never "had" the correct code to discard. So the divergence at iteration 1 is ordinary sampling variance, not an effect of STITCH. What *is* attributable to STITCH is only what happens from iteration 2 onward, once real feedback (raw tool output or interpreter directives) enters the conversation. That distinction is what separates the three categories below.

## 1. True interpreter-derailment — `simple_cpu_alu`

This is the one clean, systematic case, but it is not "derailment of correct code" — it is **misdiagnosis that prevents recovery from an already-wrong first sample.** `raw_adv` iteration 1 passed immediately with all five ports declared (`A`, `B`, `op`, `result`, `zero`). `sem_adv` iteration 1 — an independent sample — silently dropped `B` from the port list while still referencing it in the body (`result = A + B`), causing `port_mismatch`. Verilator flags this as `UNDRIVEN`, and the interpreter's canned template for that code assumes the flagged identifier is a *declared output missing an assignment*:

```
*** CRITICAL: Output 'B' is never assigned. ***
Add an assignment: 'B = <value>;' in your always block or use assign.
```

But `B` isn't an output missing an assignment — it's an **input port omitted from the port list entirely**, a categorically different bug that Verilator's `UNDRIVEN` check also happens to catch. The model followed the directive literally: iteration 2 adds `wire [3:0] B; // declare B as a wire` (declaring it as a floating internal signal, per the directive's suggested fix), and never once adds `B` back to the port list across all 6 iterations — by iteration 6 it's even attempting `assign B` on what should be an input. The directive is factually correct about *what* fired, but wrong about *what kind of problem it is*, and actively steers the model toward a plausible-looking non-fix. `raw_adv`'s unfiltered iverilog `port_mismatch` error (no interpretation layer at all) would have told the model exactly what was missing, but `sem_adv`'s prompt buries that under "Read the SEMANTIC DIRECTIVES carefully — they give you the exact fix," which in this instance they don't.

## 2. Protective-regime failure — `full_adder`

`full_adder`'s iteration-1 code is **byte-identical** between `raw_adv` and `sem_adv` — both redeclare `sum`/`cout` as `wire` after they're already declared as output ports in the module header, a duplicate-declaration compile error. Since it's identical, this isn't a sampling-variance story at all: this is one bug that both tool-augmented conditions inherit equally. `baseline` alone recovers from it in 2 iterations (bare iverilog error + a one-line hint is apparently enough). Neither `raw_adv` nor `sem_adv` recovers in 6 iterations, and the interpreter did fire on `sem_adv` (`WIDTHTRUNC`/`WIDTHEXPAND` at iterations 2–3, `UNUSEDSIGNAL` at 4–5) — real, on-target directives, not garbage — yet the model still never fixes the actual duplicate-declaration problem within budget. Per Table 7's protective-regime definition, this is not "STITCH caused harm" — `sem_adv` performs no worse than `raw_adv` here (both fail all 6/6) — it's that **STITCH failed to provide the protective effect it's supposed to provide**, and notably so did the plain tool-output condition. That points at a shared cause upstream of interpretation: the sheer verbosity of the three-layer tool dump (Verilator + iverilog + Yosys, all conditions where `use_tools=True`) may be what's overwhelming this model on this module, not the interpreter specifically.

## 3. Noise, not harm — `gray_counter_4bit`

`semantic_fired == 0` for all 6 `sem_adv` iterations — the interpreter never engaged, at any point, for this module. `raw_adv` iteration 1 passed with the textbook-correct `assign gray_out = bin ^ (bin >> 1);`. `sem_adv` iteration 1 — again, an independent sample — hand-expanded the same idea but got the bit order wrong (`{bin[0], bin[3]^bin[2], bin[2]^bin[1], bin[1]^bin[0]}`, which puts `bin[0]` where `bin[3]` belongs), and even left behind a comment showing it knew the simpler correct form (`// or, using the XOR assignment / // assign gray_out = bin ^ (bin >> 1);`) but chose the wrong hand-written one anyway. Since STITCH never fires here, there is nothing to attribute to it; the regression is pure single-run variance, and the model simply failed to self-correct through iverilog-only feedback within 6 tries. This is the case that should be pulled out of "harmful" and counted as unexplained variance, per the corrected Number 2 definition below.

## Net effect on the regime tally

Re-running Phase 1's Number 2 (baseline vs. `sem_adv`, gated on `semantic_fired > 0`) drops llama3.1's `harmful` count from 4 to 3: `full_adder`, `simple_cpu_alu`, `sync_fifo_8` remain (interpreter fired in all three), and `gray_counter_4bit` moves to a new `unexplained_variance` bucket (interpreter never fired). Of the 3 that remain, only `simple_cpu_alu` is a clean case of the interpreter's own text causing the stall (misdiagnosis); `sync_fifo_8`'s stall is a mix of iteration-1 sampling variance plus a genuinely garbled directive at iteration 3 (`"Width expansion on 'h0'"` — the signal-name-extraction regex grabbed a hex-literal fragment as if it were an identifier, a real extraction bug, general to the interpreter and not llama3.1-specific); and `full_adder` is a protective-regime failure shared with `raw_adv`, not an interpreter-specific harm. So of the "3 harmful" modules, only 1 is unambiguous evidence that the interpreter's directive text itself is the proximate cause of the stall — the other 2 involve either upstream sampling variance or a shared tool-verbosity problem. This should be stated at that resolution in the paper, not rounded up to "the interpreter derails correct generations in 3/20 modules."
